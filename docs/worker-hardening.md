# Explicit worker hardening (0.24)

Worker, offline-check, trusted-renewal and dependency-preparation sandboxes now share `src/sandbox-policy.ts`. The policy explicitly requires a user namespace, disables/asserts disabled nested user namespaces, drops all capabilities and creates a UTS namespace with a fixed worker hostname. PID/IPC/network isolation and existing mounts are preserved. A cgroup namespace is requested when available; service resource limits remain independently enforced by the outer cgroup.

`src/sandbox-launch.py` runs Python in isolated mode, builds a native-ABI libseccomp filter into a private in-memory descriptor, then execs bubblewrap. Bubblewrap loads the filter after setting up the sandbox and closes the descriptor before executing the worker. No generated filter file is placed in a writable worktree or profile. Missing runtime support, an unsupported ABI or filter-construction error refuses execution; there is no unfiltered retry.

The filter denies namespace/mount manipulation, tracing, kernel BPF/performance interfaces, keyring manipulation, module/kexec/reboot operations, file-handle opening and userfaultfd. Namespace flags on clone are refused. clone3 returns ENOSYS so normal libc thread/process creation can fall back to clone; ordinary threads, forks, filesystem calls and the selected provider relay remain usable. This is a targeted deny policy, not an exhaustive syscall allowlist. Native x86-64 and arm64 are supported in source; only x86-64 Linux was exercised here. Other ABIs fail closed.

The implementation follows the [bubblewrap source](https://github.com/containers/bubblewrap/blob/v0.11.1/bubblewrap.c) and [libseccomp API definitions](https://github.com/seccomp/libseccomp/blob/main/include/seccomp.h.in). No host AppArmor, user-namespace policy, capabilities, procfs protections or adapter ceilings are relaxed. In particular, Codex repository execution remains disabled. A native CLI requiring prohibited nested namespaces must remain unsupported until it has an independently safe execution design.

Linux tests verify zero effective/bounding capabilities, NoNewPrivs and seccomp status, a private hostname, denied sensitive calls, successful ordinary threads/forks, existing filesystem/Git/network restrictions, access-only credentials, trusted renewal and dependency isolation. Actual provider tasks and account flows are not acceptance tests for this source change. A new native CLI version may still require compatibility verification.
