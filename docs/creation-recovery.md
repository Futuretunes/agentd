# Task and project creation recovery

Before creating a task or project, the browser saves a random request ID and the request content in this tab's session storage. If a response is lost, retrying the same request reuses that ID. The runner records a session-scoped ID, canonical content hash and result ID in the same SQLite transaction as the new task/project. A replay returns that original result, including after a service restart. It does not submit an agent run or bypass approval. Reusing an ID with different work is refused.

The browser removes its pending receipt after a confirmed response. If the user edits an uncertain request, it asks before creating separate work; the earlier request might already have completed. Storage failures block sending instead of silently losing recovery information. Sign-out clears drafts and pending browser receipts. This recovery is scoped to the same authenticated browser session: after sign-out, session expiry, a different browser or an application restart that invalidates sessions, inspect History before sending again. Server receipts deliberately outlive client storage; no automatic receipt purge is implemented while task/project history is retained.

Receipts store content hashes and result IDs, not prompts or project names. The tab's pending request contains the same private input as the draft and is cleared on sign-out. Local administrator callers may supply a request ID in their separate local scope; existing private CLI callers without one retain legacy behavior. Browser creation requests require IDs, so stale cached clients must refresh.

Task schema 2 adds the receipt table with a unique session/request key. Version-1 schema is validated before migrating; migration and startup recovery share a transaction. Unsupported future versions and corrupted current schemas fail before work starts. Managed rollback restores the matching pre-update application and state; a schema-1 application cannot open schema-2 state. Native account profiles remain outside task-state rollback.

This is the creation part of R10, not a claim that all actions are asynchronous or idempotent. Git preparation can still block the event loop, and other mutations have their own recovery semantics. SQL results/receipts are atomic; filesystem preparation before project insertion can leave an unregistered directory on failure and is not automatically deleted as part of this change.
