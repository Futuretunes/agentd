# Sensitive-data review and publishing safeguards

Review and publication use `src/sensitive-data.ts`. Filename rules cover environment files, native auth/credential files, npm/Python/netrc/Git credential files, common SSH identities, AWS credential/config files and private-key/container extensions. The rule deliberately remains conservative, including examples and public-key siblings; there is no GUI bypass.

Changed blobs on both sides of a review are scanned. Every outgoing commit is scanned separately before publishing, so removing a credential in a later commit does not hide the earlier exposure. Commit messages and PR title/body are also checked. Known private-key/provider/cloud credential signatures and a narrow credential-assignment heuristic produce only generic findings, never matched values. Suspect review patches are withheld entirely. Review findings block revision reuse, commit and publication through existing approval gates. Exact trees and publication fingerprints remain authoritative.

Limits: 1 MiB per unique blob, 4 MiB across a review/publication scan and 1,000 changed files per revision. Existing subprocess/output and diff limits can be stricter. Incomplete/unsupported scans fail closed. Blob IDs are taken from literal-path Git tree metadata, not interpolated shell commands. Deleted content is also scanned because it appears in diffs. This can require separate operator handling for credential-removal changes. Binary classification uses numstat NUL records and NUL-byte content, not phrases in text.

This is a heuristic safety net, not complete data-loss prevention. Arbitrary passwords, obfuscated/encoded values, undocumented token formats and secrets outside changed blobs can be missed. Model prompts/answers, logs, uploads, existing history outside outgoing revisions and remote content are not retrospectively scrubbed. Snapshot creation may already have placed a blob in the local Git object database before review refusal. Do not treat refusal as credential rotation, secure erasure or history remediation. No secrets are sent to a scanning service. False positives and oversized/binary changes require separate review; no unsupported automatic rewriting occurs.
